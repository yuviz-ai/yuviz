# PRD: Database-Enforced Row-Level Security for Tenant Isolation

## Problem

Every tenant boundary in yuviz today is a hand-written `WHERE tenant_id = $1` clause, repeated across five services (config, campaigns, toolexec, knowledge, conversation) that all share one Postgres database. There is no independent layer that catches the query someone forgets to scope — a missing clause in a new endpoint, a copy-pasted query that drops the filter, a raw SQL debug script run against production — silently returns another tenant's rows. Verified this session: the role every service connects as (`POSTGRES_DSN`) is `rolsuper=t, rolbypassrls=t`, so even if RLS policies existed today they would be inert for every one of these services. This PRD closes that gap: RLS becomes a second, independent enforcement layer that holds even when the application-layer filter is wrong or absent.

## How this is solved elsewhere

Postgres RLS for multi-tenant SaaS has a converged shape across the ecosystem (Supabase, and the pattern described by multiple independent Postgres RLS practice guides): enable RLS per tenant-scoped table, add a policy comparing the tenant_id column to a per-request session GUC (typically `app.tenant_id` or `app.current_tenant_id`) via `current_setting()`, and set that GUC with `SET LOCAL` — never plain `SET` — immediately after acquiring a connection and before the tenant-scoped query. `SET LOCAL` scopes the value to the current transaction; with a connection pool, a request that used `SET` would leak its tenant into whatever request reuses that connection next. The other converged point: the role the application connects as must be non-superuser and must not carry `BYPASSRLS` — granting bypass to the app role (which is effectively what yuviz has today) defeats the entire mechanism regardless of how many policies exist. A materially different design used for the platform/cross-tenant bypass problem yuviz also has: some guides recommend a *second role* with `BYPASSRLS` reserved for migrations/ETL/support tooling and kept out of request-serving code paths; others recommend a *policy branch* — e.g. `USING (tenant_id = current_setting('app.tenant_id')::uuid OR current_setting('app.is_platform', true) = 'true')` — so the same app role and the same connection pool serve both scoped and platform-scoped requests. yuviz already has both request shapes on one process (per-request tenant users and `tenant_id IS NULL` platform accounts per `services/config/deps.py`), so a second role would mean routing platform-scoped requests through a second pool/DSN per service — more moving parts than a policy branch, but a policy branch means the "you are platform-scoped" signal is asserted from the application and trusted by the database, which needs its own scrutiny. This PRD does not resolve that fork; it is called out as an open question below because the answer changes both the schema (extra policy per table) and the connection code (one pool vs. two) in every service.

One more convergent recommendation this PRD adopts: `FORCE ROW LEVEL SECURITY` on every tenant-scoped table, not just `ENABLE ROW LEVEL SECURITY`. `ENABLE` alone still exempts the table owner from its own policies — if the new non-superuser app role is also made the owner of these tables (a natural default), `FORCE` is what actually makes the policy bind. And the fail-safe-default convention — no session variable set means the query matches zero rows, not all rows — is treated here as a hard requirement, not a nicety: a service that forgets to `SET LOCAL app.tenant_id` should get an empty result set, never a cross-tenant leak.

## Scope

- In: An RLS policy exists on every table that has a tenant-scoping column, enforcing `tenant_id = <the session's tenant>` (or the platform-bypass branch, per the resolved open question) for every SELECT/INSERT/UPDATE/DELETE.
- In: A new, non-superuser, non-`BYPASSRLS` Postgres role that owns (or is granted exactly the privileges it needs on) these tables, with no DDL rights, is what every one of the five services connects as at runtime.
- In: Every one of the five services (config, campaigns, toolexec, knowledge, conversation) sets a per-request session variable (e.g. `SET LOCAL app.tenant_id`) immediately after acquiring a connection for any request that touches a tenant-scoped table, sourced from the same already-resolved tenant identity the existing app-layer `WHERE` clauses use today — not a new identity-resolution path.
- In: Platform-scoped requests (`tenant_id IS NULL` users/service accounts per `services/config/deps.py`) continue to work under RLS — the specific mechanism is an open question below, but "still functions" is in scope regardless of which mechanism is chosen.
- In: A negative-test suite (new) that proves cross-tenant rows are unreachable at the database layer when the session is set to a different tenant, run against the new role directly — independent of and in addition to the existing app-layer test suites.
- In: A README (new, in this feature's `.sdlc` folder and/or `docs/`) documenting what changed, why, the new role's credentials/provisioning path, and how a new table or a new service entry point must wire the session variable to stay covered.
- Out: Unifying the `tenant_id` type inconsistency across tables (UUID FK on `agents`, `custom_apis`, `provider_configs`, `knowledge_bases`, etc. vs. `calls.tenant_id` as a TEXT slug). This PRD requires each table's policy to work correctly with whatever type that table already has — not to migrate any column's type.
- Out: Changing which tenant a request resolves to, or any change to the existing JWT/session identity model in `services/config/deps.py`. RLS consumes the identity that already exists; it does not change how identity is established.
- Out: Extending RLS to tables that have no tenant-scoping column today (platform-global reference tables, e.g. `tenants` itself, `carriers`) unless a service's existing app-layer code already treats them as tenant-scoped.
- Out: Performance tuning beyond what's needed for correctness (e.g. adding a composite index only if a specific table's existing index does not already lead with `tenant_id` and a query plan regression is observed) — this is a defense-in-depth security change, not a performance project, and any index change found necessary should be called out explicitly rather than done silently.

## Acceptance criteria

1. Given the new Postgres role, when `SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = <new role>` is run, then `rolsuper = false` and `rolbypassrls = false`.
2. Given a tenant-scoped table, when its RLS state is inspected (`pg_tables.rowsecurity` / `pg_class.relforcerowsecurity`), then both RLS and FORCE RLS are enabled for every table in the tenant-scoped set enumerated in the design.
3. Given a connection authenticated as the new role with `SET LOCAL app.tenant_id = '<tenant A>'`, when a query selects rows belonging to tenant B on any tenant-scoped table, then zero rows are returned (not an error, not tenant B's rows).
4. Given a connection authenticated as the new role with no session variable set at all, when a query selects from any tenant-scoped table, then zero rows are returned (fail-safe default), not all tenants' rows.
5. Given a connection authenticated as the new role with `SET LOCAL app.tenant_id` set to tenant A, when an INSERT or UPDATE attempts to write a row with `tenant_id` = tenant B, then the statement is rejected by the policy's `WITH CHECK` clause, not silently accepted.
6. Given the resolved platform-bypass mechanism (see Open questions), when a platform-scoped request (`tenant_id IS NULL` user or a known service account) runs today's cross-tenant queries (e.g. Conversation's startup prewarm, vobiz's per-call telephony lookup), then those queries return the same rows they return today, unchanged.
7. Given each of the five services' existing test suites, when they are run end to end against a database where the app role has been switched to the new non-superuser role and RLS is active, then all suites pass with no test rewritten to route around RLS (a test that needs a workaround is itself a finding, not a pass).
8. Given a service request handler that acquires a connection for a tenant-scoped query, when the request completes (success or error), then the session variable does not leak to the next request that reuses the same pooled connection — verified by a test that runs two requests for two different tenants back-to-back on a pool with `min_size=1`/reused connections and asserts the second request never sees the first tenant's `app.tenant_id`.
9. Given a request whose tenant identity fails to resolve (the identity-resolution step itself errors or returns nothing), when the connection is acquired for a tenant-scoped query, then the request fails closed (empty result or explicit error) rather than proceeding with the session variable unset and silently falling into the fail-safe-zero-rows path being mistaken for "no data" by the caller — this must be an explicit, tested failure mode, not an assumption.
10. Given the `calls` table specifically (TEXT tenant slug, not a UUID FK), when its policy is exercised with the negative test in (3), then it isolates correctly using the slug value the app already resolves — without requiring any change to the column's type or to existing queries that already work with the slug.
11. Given the README deliverable, when a new engineer reads it, then it states: which role each service now connects as, exactly where in each service's connection-acquisition code the session variable is set, which tables carry RLS policies, how the platform-bypass mechanism works, and what a new tenant-scoped table or new service must do to stay covered (this is a checklist an implementer can follow, not a narrative).
12. Given the migration/rollout path, when the new role is introduced, then there is a verified rollback: a documented way to revert every service's `POSTGRES_DSN` to the prior role without requiring the RLS policies or the new role to be dropped first (so a rollout that breaks production under the new role can be undone in a service-by-service DSN change, not a schema change, under time pressure).

## Constraints

- Tenant identity must be sourced from the existing resolution path — `services/config/deps.py`'s `get_current_user`/`get_authenticated_user` and the equivalent already-resolved identity each of the other four services carries into its query layer — not re-derived. This PRD adds a database-layer check on top of that identity; it does not add a second place identity gets decided.
- Platform-scoped accounts are identified today by `tenant_id IS NULL`, not by role name (Lesson 24 / `services/config/deps.py`). Whatever bypass mechanism is chosen must be driven off that same predicate, not off `role == "superadmin"` — a role-based check would (as it did before) miss the Conversation and vobiz service accounts that authenticate as `role="viewer"` with a NULL tenant.
- Connection acquisition today is `async with (await get_pool()).acquire() as conn` per operation, one process-wide pool per service (`services/config/db.py`, and the equivalent `db.py` in campaigns/toolexec/knowledge; conversation's pattern should be confirmed against its own module before implementation). The session-variable `SET LOCAL` must be issued on every acquired connection before a tenant-scoped query runs, inside the same transaction as that query — `SET LOCAL` only holds until the enclosing transaction ends, so a query issued outside an explicit transaction block needs the design to specify how the variable and the query share one transaction.
- `calls.tenant_id` is TEXT (a slug), while `agents.tenant_id`, `custom_apis.tenant_id`, `provider_configs.tenant_id`, `knowledge_bases.tenant_id` (and others) are UUID FKs to `tenants.id`. Per-table policies must cast/compare against whichever type that table already uses; this PRD does not standardize the column type.
- Schema is applied via `psql -f` with no `ON_ERROR_STOP` by default (Lesson 13/14) — any DDL shipped for this change (role creation, `ALTER TABLE ... ENABLE/FORCE ROW LEVEL SECURITY`, `CREATE POLICY`) must guard destructive or order-sensitive statements the same way existing schema changes do, and a reviewer must verify against a database with real rows, not an empty one (Lesson 10/13).
- The current superuser role must remain available for migrations, `psql -f` schema application, and any admin tooling that legitimately needs to bypass RLS (e.g. `scripts/create_superadmin.py`, `scripts/seed_default_config.py`) — this PRD replaces which role *services* connect to at runtime, not the role used to apply schema or run one-off admin scripts.

## Open questions

1. Platform-bypass mechanism: a policy branch checking a session flag/GUC (e.g. `app.is_platform`) trusted from the application, versus a second Postgres role carrying `BYPASSRLS` used only by platform-scoped connections (which then means each service either opens a second pool on a second DSN, or the same pool switches roles per request via `SET ROLE`). This changes both the schema (one extra policy clause per table vs. none) and the connection code (one pool vs. two, or a `SET ROLE`/`RESET ROLE` pair per request) in every one of the five services — the PRD cannot pick this without the architect weighing the trust boundary (an app-asserted session flag is only as trustworthy as the code path that sets it) against the operational cost of a second role/pool per service.
2. Per-table policy predicate for the TEXT-slug case (`calls.tenant_id`): does the session variable get set as the slug directly, or does it get set as the tenant UUID and each TEXT-keyed table's policy do a join/lookup to `tenants.id`/`tenants.slug` to compare? The former is simpler but means the session variable's shape is not uniform across tables; the latter adds a subquery to every policy on that table. This is a per-table decision the architect needs to make table by table, not a blanket rule.
3. Ownership of the tenant-scoped tables: does the new non-superuser role become the table owner (required for `FORCE ROW LEVEL SECURITY` to bind on that role, per the researched convention), or does an existing owner role stay the owner and the new role is only granted DML? This affects whether `ALTER TABLE ... OWNER TO` needs to ship as part of this change and who is authorized to run it.
4. Scope of "tenant-scoped table": the request names five services but not an exhaustive table list. The architect must enumerate every table with a `tenant_id` (or equivalent) column across all five services' schemas as part of design — this PRD sets the acceptance bar ("every tenant-scoped table has a policy and a negative test") but does not itself enumerate the tables.
5. Does `conversation`'s connection-acquisition pattern match the `async with (await get_pool()).acquire()` shape confirmed for config/campaigns/toolexec/knowledge, or does it hold a connection differently (e.g. per-call-session-lifetime, given it's the live-call-handling service)? If conversation holds a connection across multiple logical "requests" within one call session, `SET LOCAL`'s per-transaction scope needs a different wiring than the other four services — this must be confirmed during design, not assumed.
