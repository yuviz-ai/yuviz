# PRD: Easy and Advanced agent creation for non-technical users

## Problem
A business owner who wants a voice or chat agent has to work through a six-step console wizard (identity, language and voice, limits, advanced, knowledge and tools, review). That wizard shows engineer concepts such as "overrides the STT/TTS provider's own language", provider engines ("macOS say / Kokoro / ElevenLabs") and LLM config pickers. They cannot tell whether the resulting prompt is any good, and when the agent behaves badly after a test call, the only fix is to hand-edit a system prompt they do not understand.

## How this is solved elsewhere
Market research (limited to search snippets; anything not stated is unverified):
- **Templates by industry/use case:** Synthflow offers "Browse Templates" (prompt, voice and often actions preloaded, filterable by industry and call type). ElevenLabs Agents has a Business Agent type with category and specialization. Retell AI has "from template" agents (thinly verified).
- **Website-URL bootstrap:** ElevenLabs Agents takes your business URL at creation, auto-generates an initial prompt and seeds the knowledge base. Intercom Fin's whole onboarding is "give it your content (help center or public URLs) first", then preview, then roll out to a test audience.
- **Plain-language prompt editing:** Vapi's "Generate" function rewrites the system prompt from a described change. ElevenLabs frames the prompt as six sections (personality, environment, tone, goal, guardrails, tools), so the generator has structure to fill.
- **Test loop:** Retell AI offers LLM-simulated callers with defined personas and metrics. That is aimed at engineers and is the most expensive thing on this list.
- **Genuine fork:** (a) URL/doc ingestion up front (ElevenLabs, Fin) versus (b) describe-in-words (Vapi). Ingestion gives factual grounding but needs a crawler (SSRF and tenant-scoping work). Describe-in-words is cheap but cannot supply facts such as prices and hours.

**Recommendation.** Easy mode is "choose a job for your AI receptionist", not "pick a template and edit a prompt". The user never has to understand agents, prompts, LLMs, speech recognition, providers, workflows or configuration. The flow is: What should my AI receptionist do? -> Tell it about my business -> Choose how it speaks -> Test it -> Fix anything that's wrong -> Put it to work. Under the hood each job is a complete shipped template (the Synthflow/ElevenLabs shape) and Easy creation is deterministic, with no LLM call. Advanced is today's six-step wizard. The only way a prompt changes in Easy is the plain-language "Something wrong?" fix loop (Vapi-style), always with before/after review and one-level undo. Agents made in Easy start inactive and go live only on an explicit "Put it to work" (Fin's preview-before-rollout idea, using the status column we already have). We do not copy Retell's simulation testing, and we cut website crawling from v1 (see Open questions). Every prompt, shipped or generated, must contain how to speak like a human, guardrails, and task-specific instructions that make the agent good at its job.

## Scope
- In: Two modes on the new-agent screen. Easy is the default; Advanced is today's six-step wizard and fields. Advanced's "Generate with AI" keeps its UI but gains the prompt guarantees below.
- In: The Easy flow with exactly six steps: What should my AI receptionist do? -> Tell it about my business -> Choose how it speaks -> Test it -> Fix anything that's wrong -> Put it to work.
- In: Step 1 lists jobs (complete shipped templates: greeting, prompt, handoff rule, and a conversation flow where the use case needs one) across inbound, outbound and chat-suited use cases (for example appointment booking, FAQ/support, lead qualification, order status, plus the 4 existing). Each job declares its channel and shows, before creation, what it does, what it will not do, and when it hands off to a person.
- In: Step 2 takes name, business name and up to 1,000 characters of business facts. Step 3 ("how it speaks") is language plus a plain voice choice, shown only when the tenant has more than one voice. No tone, prompt or other template field is editable in Easy.
- In: Every template prompt and every generated or revised prompt contains three parts, each under its own heading: how the agent speaks like a human, guardrails, and doing the job well.
- In: Easy-created agents are created inactive (the existing agent status) and stay so until the user clicks "Put it to work", which sets them active.
- In: A test-only path so an inactive agent can be tested. Verified today: it cannot be (see Constraints), so this is new work, gated by tenant and role.
- In: An Easy variant of the Test step, in plain language, for voice jobs; and a text-conversation Test step for chat-suited jobs, whose transcript is stored with the existing test-session records.
- In: Each agent created from a shipped template records that template's identifier and version.
- In: "Fix anything that's wrong": the user describes a problem in plain words, the system proposes a revised prompt as before/after, Accept is refused if the stored prompt changed since the proposal, and the latest accepted change can be undone (one level). Revisions never persist customer-specific data from a transcript as instructions.
- In: After "Put it to work", an Easy confirmation that says plainly the receptionist will not receive anything until a phone number or chat channel is assigned, with a link to where that is done. This is a stated v1 limitation: Easy does not assign numbers or channels.
- In: One new piece of stored state for undo: per agent, the prompt in force before the latest accepted revision and the accepted prompt (or its hash). Plus the template id and version on the agent.
- Out: Website/URL crawling and import; third-party doc connectors (Confluence, Notion).
- Out: Simulated-caller or batch test suites, auto-scored quality metrics.
- Out: Free-text "describe your agent" generation in Easy (it remains in Advanced); a template marketplace or any stored per-tenant template.
- Out: Phone-number or chat-channel assignment inside Easy; a tenant-level default-provider setting.
- Out: Multi-level prompt history. One level of undo is sufficient for this release.
- Out: Changes to call-flow/workflow authoring, voice cloning, or telephony number assignment.

## Acceptance criteria
1. Given an admin opens the new-agent screen, when it loads, then Easy is shown by default and an "Advanced" control opens the existing six-step wizard, which sends the same fields to create an agent as it does today and still creates agents active.
2. Given Easy, when the user progresses, then the six steps appear in this order with these exact titles: "What should my AI receptionist do?", "Tell it about my business", "Choose how it speaks", "Test it", "Fix anything that's wrong", "Put it to work".
3. Given the job list, when shown, then it has at least 8 jobs (the 4 existing plus at least 4 new), including at least 2 inbound and 1 chat-suited, each with a label, a one-line blurb and its channel (phone in, phone out, or chat).
4. Given a job whose channel needs something the tenant lacks (voice jobs need speech recognition and a voice; every job needs an AI service), when the list is shown, then that job is disabled with the matching criterion-10 message; and when a create request names a template whose assigned configs do not fit its channel (for example a voice template with no STT or TTS config), then the server rejects it with 400 and creates nothing.
5. Given a job is selected, when the screen renders and before Create is available, then three non-empty, template-authored read-only blocks are visible ("What it does", "What it won't do", "When it passes the call to a person"), and the third contains the template's handoff rule text; no control edits them.
6. Given Easy, when a step renders, then the only editable controls are: step 2 name, business name, business facts; step 3 language and, only when the tenant has more than one voice, a "Voice" dropdown; a test asserts this exact set.
7. Given Easy in any state (including error and empty states, the criterion-10 messages, the Test step and the Put it to work confirmation), when it renders, then no text contains "agent", "prompt", "LLM", "STT", "TTS", "provider", "workflow", "configuration", "engine", "latency" or "model" outside the collapsed technical view; tenant-supplied config display names in dropdown options are exempt.
8. Given name or business name is empty, or business facts exceed 1,000 characters, when Continue or Create is clicked, then an inline error appears and no create request is sent.
9. Given a valid Easy form, when Create is clicked, then the agent is saved with the template's prompt, greeting and flow with the user's name, business name and facts substituted, and no LLM call is made during creation.
10. Given a tenant with zero configs for a role the job needs (AI service, speech recognition, or voice), when the Easy screen loads or Create is clicked, then a plain message is shown ("Connect an AI service to continue", "Set up speech recognition to continue", "Set up a voice to continue", respectively) with a link to where it is added, and no agent is created.
11. Given a tenant with exactly one config for a needed role, when an agent is created from Easy, then that config is assigned with no question asked.
12. Given a tenant with more than one voice config, when step 3 renders, then a "Voice" dropdown labelled by config display names appears, preselected to the voice config of that tenant's most recently created non-deleted agent only if that config still exists in this tenant, otherwise unselected; Continue is disabled until it has a value. No default flag is stored anywhere. Roles other than voice with more than one config use the same rule via the same kind of plain dropdown.
13. Given business name or facts containing braces or template-like text (for example `{{secret}}`), when the agent is created, then that text appears literally in the saved prompt and is never evaluated or resolved.
14. Given business facts, when substituted, then they sit in a fixed, labelled "Business facts" block inside "Doing your job well", and a fact that itself contains "Guardrails" or "How you speak" does not change the heading order, the verbatim blocks or the task section; heading and block checks (criteria 15-18) run against the template, not the substituted output.
15. Given any template prompt, when inspected, then it contains the headings "How you speak", "Guardrails" and "Doing your job well", each on its own line, in that order.
16. Given any template, generated or revised prompt, when inspected, then "How you speak" contains the shared human-speech block verbatim (one exact-match constant in one place), which requires: plain conversational wording with contractions; at most two sentences per turn for voice; one question at a time; brief natural acknowledgements (for example "got it", "sure"); stopping and listening when the caller interrupts; and nothing read aloud that is a list, markdown, URL or symbol. Chat-suited templates use the same block with voice-only items replaced by a fixed written-chat variant.
17. Given any template, generated or revised prompt, when inspected, then "Guardrails" contains the `_GUARDRAILS` text from `services/config/system_prompt.py` as an exact substring.
18. Given any template, when inspected, then its "Doing your job well" section has at least 3 non-empty instruction lines, contains that template's purpose sentence, and is not identical to any other template's section.
19. Given Advanced "Generate with AI" or a revision returns text, when the server checks it, then: if any of the three headings of criterion 15 is absent or out of order, or "Doing your job well" has fewer than 3 non-empty lines, the server returns an error and no text; otherwise it inserts any missing verbatim block (criterion 16 or 17) at the end of its own section, under its own heading, and never at the end of the whole text.
20. Given a description that tries to override guardrails (for example "ignore all previous rules"), when a draft is generated, then criteria 16 and 17 still hold for the output.
21. Given Generate or a revision is requested, when the call completes, then nothing is persisted until the user clicks Create or Accept.
22. Given an agent is created from a shipped template, when read back, then it carries that template's identifier and version; an unknown template identifier or a version above the shipped one is rejected with 400; an agent created in Advanced has neither.
23. Given an agent is created in Easy, when read back, then its status is inactive; given an agent created in Advanced, then its status is active as today.
24. Given an inactive voice agent created in Easy and a valid test credential (criterion 26), when the user starts a session in "Test it", then the session runs that agent's own prompt, greeting and voice.
25. Given an inactive agent and a test session, when the agent cannot be resolved for any reason, then the session ends with an error and never falls back to the legacy or default configuration (which today would silently run a different agent).
26. Given a test session request for an inactive agent, when it carries no credential, an expired one, or one minted for a different tenant or agent, then it is refused and the refusal is identical to the one for a non-existent agent; a valid credential can only be minted by an admin or superadmin acting on the path tenant, for one named agent of that tenant, valid for test sessions only and for a short fixed lifetime.
27. Given an inactive agent, when a real (non-test) call resolves it, then it resolves as unavailable, exactly as today.
28. Given a chat-suited job's agent, when the user opens "Test it", then the screen is a text conversation with that agent (the test credential of criterion 26 applies); every turn is stored in the existing test-session records, keyed by session id with the tenant's slug and the agent id and direction "test", and is readable by the fix step.
29. Given a voice job's "Test it" step, when it renders, then it is an Easy variant (a plain "Start talking" / "Stop" control, a live transcript, plain status words) and passes criterion 7; the existing test page with its engineer text stays unchanged for Advanced and the agent page.
30. Given an inactive agent created in Easy, when the user clicks "Put it to work", then its status becomes active, and a confirmation says plainly that it will not receive calls or chats until a phone number or chat channel is assigned, with a link to where that is done; the agent is never activated by any other Easy action.
31. Given an agent created in Easy, when opened on the existing agent page, then all its fields, including status, are editable there as for any agent.
32. Given a finished test session with at least one stored transcript entry for this agent, when the user opens "Fix anything that's wrong", then a text box accepts up to 1,000 characters and the revise action takes that session's id.
33. Given a test session that never connected or has no transcript entries, when the user opens that step, then it says a test is needed first and no revise request is sent.
34. Given a problem description, when submitted, then a proposed revised prompt is shown as before and after, the stored prompt is unchanged until Accept, and the proposal meets criteria 15-19.
35. Given a transcript, when a revision is proposed, then the server rejects it (no text returned, agent unchanged) if it contains a customer-specific token absent from the base prompt and from the user's problem text. Customer-specific means: an email address, a phone number (7 or more digits allowing spaces, dashes, brackets and a leading +), any run of 6 or more digits (order, account, booking, reference or card numbers), a date-of-birth pattern, or a substring of 40 or more characters copied verbatim from a caller line in the transcript.
36. Given a proposal rejected under criterion 35, when the user sees the result, then the message reads "That fix would copy details from a specific customer into the instructions. Describe the problem in general terms and try again." with a pre-filled example, the user's problem text is kept in the box, and the message does not echo the offending token.
37. Given the meta-prompt for revision, when inspected, then it instructs the model to generalise rather than copy caller names, addresses, numbers and ids; caller names and street addresses are not deterministically detectable, so for them the before/after review is the control, and this PRD does not claim otherwise.
38. Given Accept is clicked, when the request is made, then it carries the prompt the proposal was based on (or its hash); if the stored prompt differs, the server refuses with 409, changes nothing, writes no slot, and the user is told to re-run the fix.
39. Given Accept is clicked with proposed text, when the server handles it, then it re-runs criteria 15-19 and 35 on the submitted text; if any check fails, the response is 400 and nothing changes.
40. Given a valid Accept, when saved, then the prompt equals the proposed text and the agent's slot stores the prior prompt and the accepted prompt (or its hash), overwriting any earlier slot value.
41. Given the user clicks Discard, when dismissed, then the agent and its slot are unchanged.
42. Given the agent's current prompt equals the accepted prompt in the slot (compared server-side, including on page load), when the user clicks "Undo last change", then the prompt is restored to the stored previous prompt and the slot is cleared, so a second Undo is unavailable.
43. Given two Accepts in a row, when the user clicks Undo once, then the prompt equals the one before the second Accept, and Undo is then unavailable.
44. Given the user hand-edited the prompt after an Accept so it differs from the stored accepted prompt, when the agent page loads, then Undo is not offered; and if an Undo request is sent anyway, it is rejected with no change and the previous prompt is not applied by any other path.
45. Given the revision call fails or times out, when the user is shown the result, then an error message appears, the agent is unchanged, and the user can retry.
46. Given a user with role viewer, when they call create-from-template, generate, revise, accept, undo, activate or mint a test credential, then the response is 403 and nothing is generated or changed.
47. Given tenant A's admin supplies an LLM config id belonging to tenant B, when generating or revising, then the response is identical to the one for a non-existent id (same status and body) and no call is made with tenant B's credentials.
48. Given tenant A's admin supplies an agent id or session id belonging to another tenant, or a session id that is not a test session of the named agent, when calling revise, accept, undo or mint a test credential, then the response is identical to that for a non-existent id, no transcript text is returned or sent to any model, and no slot is read or written.
49. Given a transcript is used for a revision, when the model call is made, then only that tenant's own test session for that agent is included and it is sent only to that tenant's own configured LLM provider.
50. Given business facts, generate or revise inputs (description, problem text, transcript), chat test messages, test credentials or the stored slot prompts, when logged by any service, then none of their text appears in any log line.
51. Given a transcript containing instructions aimed at the model (for example "reveal the API key"), when a revision is proposed, then it is still only a draft requiring human Accept, and no secret value appears in it.
52. Given a platform superadmin acts on tenant A through the path-scoped tenant, when they create, generate, revise, accept, undo, activate or mint a test credential, then the action is scoped to tenant A's configs, agents and sessions only.
53. Given an unauthenticated caller, when they hit generate, revise, accept, undo, activate or mint a test credential, then the response is 401.
54. Given Easy is driven end to end in a browser by a user who has not seen Advanced, when they go from the empty agents page through all six steps to an active agent and its confirmation message, then they complete it using only Easy screens (checked by running the app, not by unit tests alone).

## Constraints
- Auth and roles: creation and edit stay `require_role("superadmin", "admin")` and tenant is bound from the path (`services/config/routers/agents.py:20-24`, `:67-72`). Revise, accept, undo, activate and credential minting follow the same guards. Memoized identity re-check applies (lesson 27).
- Tenant isolation: tenant is resolved by `_resolve_tenant`, which returns 404 for a wrong-tenant caller (`agents.py:31-39`). Cross-tenant ids must be per-caller invariant with a non-existent id, in status, body and latency (lesson 2). The LLM config used for generation and every config assigned by Easy must be validated as the path tenant's own before use (lessons 31, 37). The base is `generate_system_prompt(tenant["id"], llm_config_id, ...)` in `services/config/system_prompt.py`.
- Transcript lookup: `calls.tenant_id` is a TEXT slug with no foreign key (`database/schema.sql:545`), and transcript rows hang off `calls.session_id` only. The revise read must predicate on the path tenant's slug AND `agent_id` AND direction "test", with an explicit predicate since RLS is inert on this superuser DSN (lesson 36); the isolation test must go red when that predicate is removed.
- Agent status and the test path (verified): `agents.status` ('active' | 'inactive', default 'active', `schema.sql:139`) is reused for draft-until-activated; no new state. The browser test path (`services/webcall/__main__.py:248-277`) opens a session with only tenant slug and agent slug from query parameters and no credential, and Conversation resolves it with `resolve_handler_deps` (`services/conversation/agent_resolver.py:37-66`). That calls `get_runtime_config`, which returns nothing for an inactive agent (`libs/config_sdk/providers/cache_aside.py:201`), and the resolver then logs and falls back to the legacy configuration, so today a test of an inactive agent would silently run the wrong agent. A test-only path is therefore required (criteria 24-27). Because that endpoint takes no credential today, a bypass for inactive agents there must not be reachable by anyone who merely knows two slugs, hence the minted, tenant-and-agent-bound, short-lived credential of criterion 26; its design (token versus signed request, where it is verified) is the architect's call, and the credential is a bearer-equivalent secret (lessons 16, 20, 43). Whether the existing unauthenticated access to active agents on that endpoint should also be closed is a separate finding, noted but not changed here. Real calls keep the inactive check. Advanced keeps the active default.
- Chat test: no text-conversation test session was found in the codebase beyond the voice bridge (unverified outside the files searched), so the chat-suited Test step (criterion 28) is new work that must reuse the same session and transcript records (`calls` with direction "test", `transcript_entries`) rather than a second store.
- Schema additions (the only ones), both on rows already tenant-scoped: (1) agents gets a template identifier and a template version (nullable, set only for template-created agents), validated against the shipped catalog on the server, so the catalog must be reachable server-side as well as by the UI (the architect decides how without a second source of truth); (2) the undo slot: per agent, previous prompt plus accepted prompt (or hash), carrying `tenant_id` with a tenant predicate on every read and write and its agent reference bound on `(id, tenant_id)` (lesson 36). Accept and Undo are each a single conditional update that compares the stored prompt to the expected one (base for Accept, accepted for Undo), with zero rows treated as the losing path (lesson 8). Schema apply is plain `psql -f` without ON_ERROR_STOP, so any backfill or guard must live in one DO block (lessons 10, 13).
- Prompt composition is server-guaranteed, not model-guaranteed: `_GUARDRAILS` (`system_prompt.py:35`, used at `:66`) and the shared human-speech block are checked as exact substrings on generate, revise and Accept. A missing block is inserted at the end of its own section; a missing or misordered heading is an error, not a repair (criterion 19). The meta-prompt text that asks the model to reproduce guardrails "close to verbatim" (`:31`, `:63`) changes to an exact copy. Each block lives in one place, imported by templates, generator and reviser. Accept re-verifies server-side because the client could otherwise submit unchecked text.
- Customer-data check (criteria 35-37) is a deterministic server-side pattern check plus the meta-prompt instruction; neither alone is sufficient, and names/addresses are knowingly covered only by instruction and human review.
- Template substitution: business name and facts are tenant-written text inserted as plain text only; they never reach a template engine, variable resolver or secret resolver (lesson 37). They reach the LLM vendor only via revise (as part of the prompt) and must not enter logs (lesson 33).
- Agent create/update fields (`greeting`, `system_prompt`, `stt/llm/tts_config_id`, `workflow`) in `services/config/schemas.py` (`AgentCreate`) stay as is; Easy submits through them plus the template identifier and version. Templates are shipped definitions (extending `admin-ui/lib/agentTemplates.ts`), never a stored, tenant-readable entity.
- UI: the console is `admin-ui` (Next.js with breaking changes; read `node_modules/next/dist/docs/` first per `admin-ui/AGENTS.md`). The six-step page `admin-ui/app/(console)/agents/new/page.tsx` becomes Advanced; the test page under `agents/[tenantSlug]/[agentSlug]/test/` stays as is for Advanced and gains an Easy variant (criterion 29) that must expose its session id. Do not use `Promise.all` over independent fetches on the Easy screens (lesson 21); admin-only surface (lesson 22).
- Generation is a one-shot draft that is never persisted (existing behaviour at `agents.py:73-74`); keep that.

## Open questions
1. Should website URL import (ElevenLabs/Fin style) be pulled into this release? It is the biggest factual-grounding win for non-technical users, but it adds a server-side fetcher (SSRF controls, per-tenant crawl limits, robots handling) and is out of scope as written.
