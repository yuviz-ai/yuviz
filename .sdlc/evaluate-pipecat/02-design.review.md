# Review: 02-design.md (evaluate-pipecat)
VERDICT: AMBER

1. [minor] §8 silently substitutes the PRD's named comparison target (`future_workflow_graph_model.md`, explicitly cited in PRD Scope for the workflow-builder comparison) with `services/conversation/workflow/runner.py`, asserting "this repo already has a shipped workflow runtime... the comparison is against what exists, not against a deferred roadmap doc" — but never states whether `workflow/runner.py` is the same effort as the in-progress graph-model work or a different, already-shipped mechanism, so AC14's required comparison point may go missing under a plausible-sounding substitution — fix: §8 should compare against both `workflow/runner.py` (what ships today) and name `future_workflow_graph_model.md` explicitly as the PRD requires, stating the relationship between the two rather than dropping one silently (lessons.md #7).

2. [minor] The Recommendation-block self-check (§Interfaces, item 3) bars `Adopt`/`Partial adopt` whenever criterion 1 (latency) is `worse` *or* `unknown` on a media-path stage — combined with the design's own decision to run no smoke test, every conversation-pipeline stage's latency claim is capped at `unverified`/`unknown` by construction (Interfaces §2, Claim tag rules), which means the process guarantees `Reject` or `Partial adopt` for every media-path stage regardless of what the evidence actually shows, before any stage-specific analysis happens — the design flags this in Risks as "intended, not a gap" but doesn't reconcile it with PRD AC11's weaker bar ("adopt confirms it does not regress latency," not "adopt requires latency proven non-worse") — fix: either loosen the self-check to allow `Adopt` when `unknown` is supported by strong literature-based reasoning (matching PRD's actual bar), or keep the stricter bar but say so explicitly as a scoping decision in §1, not just bury it in Risks.
