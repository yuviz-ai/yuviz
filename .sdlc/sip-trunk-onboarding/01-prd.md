# PRD: SIP Trunk Onboarding — Purchase-to-Live-Call Connectivity

## Problem
Today a tenant admin can search and purchase a phone number through the DID Service (`services/did/`), but purchasing does not make the number callable: nothing configures the carrier's side to route PSTN traffic to our Kamailio, and nothing configures the outbound (termination) leg the Campaigns/Conversation services need to place calls out through that same number. Per `docs/cloud_deployment_architecture.md` §7 this "bind number to platform trunk" step is explicitly unbuilt — an admin who finishes a purchase today has a number that looks active in the Admin UI but silently fails on the first real inbound or outbound call, with no signal at purchase time that anything is wrong.

## How this is solved elsewhere
Twilio Elastic SIP Trunking and Vonage's SIP dashboard both split trunk setup into two independently configured legs — **Origination** (carrier→customer, inbound) and **Termination** (customer→carrier, outbound) — each authenticated by either IP allowlisting or SIP username/password, never assumed symmetric (Twilio docs, Vonage SIP dashboard). Both let the customer associate a purchased or ported number with a trunk only after both legs exist. Vonage's newer onboarding wizard and Twilio's guide both end with a live test call before the trunk is called "ready" — provisioning success is not inferred from the API call succeeding, it's confirmed by placing a call. Separately, the market draws a hard line between **buying a managed number from the platform's own carrier account** (Twilio/Plivo/Vonage numbers) and **bring-your-own-trunk (BYOT)**, where the customer already owns carrier credentials and hands the platform only a SIP URI/IP to trust (Telnyx's "bring your own carrier" pitch, Plivo Zentrunk). BYOT is a materially different trust boundary — the platform must accept inbound SIP from a customer-controlled endpoint — and every vendor treats it as a separate, more advanced product tier, not a day-one feature.

Recommendation: build the managed-number path first (we already own the carrier relationship via `services/did/providers/`), split provisioning into an inbound-routing step and an outbound-credential step exactly as the market does, and gate the number's "active" status on a real test call passing rather than on the provisioning API call returning 200. Cut BYOT from this PRD — the request's phrase "purchase sip trunk" maps to the managed-number flow we already have half of; accepting an integrator's own trunk is a distinct, larger security surface (arbitrary source IPs/credentials to trust at Kamailio) that deserves its own PRD once the managed path is live and verified.

Assumption: "developer or integrator" in the request means a tenant admin (or a platform operator acting on a tenant's behalf) using the Admin UI / DID Service API — not an anonymous public signup flow. No self-serve tenant creation flow is referenced in the request or exists in scope here.

## Scope
- In: Tenant admin purchases a number through the existing DID Service search/purchase flow, and the platform automatically provisions that number's **inbound** routing (carrier configured to send PSTN calls to our Kamailio) without any manual per-number Kamailio edit.
- In: The platform automatically provisions that number's **outbound** leg (carrier-side termination credentials/trunk so Campaigns and Conversation Service can place calls out through it) once the number is assigned to an agent.
- In: Generalizing Kamailio's DID-matching gate — currently hardcoded to `$rU == "788" || $rU =~ "500[0-9]"` at `scripts/kamailio/kamailio.cfg.tpl:665`, admitting only local test extensions — so that any active, purchased PSTN number reaches the existing FreeSWITCH/Redis routing path. This is a prerequisite this feature depends on (project memory: Kamailio DID Routing Gotcha), not an optional nice-to-have: without it, every number this feature provisions will 407 at Kamailio before ever reaching Redis resolution, identically to the documented gotcha.
- In: A purchased number has a visible provisioning status (`purchased` → `provisioning` → `active` / `failed`) surfaced in the Admin UI and via the DID Service API, so an admin never sees "purchased" and assumes "callable."
- In: A "test this number" action that verifies both the inbound and outbound legs before the number can be marked active for production use — see Constraints for how each leg's test is actually mechanized, since it differs by direction.
- In: Every provisioning and test-call action is attributable (who triggered it, when, result) via the existing audit mechanism (`services/did/audit.py`), matching purchase/release today.
- Out: Bring-your-own-trunk — accepting a customer-owned SIP trunk's credentials/IP as an inbound or outbound source. Deferred per research above; own PRD.
- Out: Number porting from another carrier/provider into this platform.
- Out: SMS/messaging provisioning on the trunk — voice-only, matching today's `AvailableNumber.capabilities` scope.
- Out: Carrier cost pass-through/billing to the tenant for the number or test-call minutes.
- Out: Multi-carrier failover or automatic re-routing if a carrier's inbound/outbound leg degrades post-activation.

## Acceptance criteria
1. Given a tenant admin with role `admin`/`superadmin` purchases a number via the existing purchase endpoint, when the purchase succeeds, then the number's status is `provisioning` (not `active`) until inbound and outbound legs both confirm success.
2. Given a number in `provisioning`, when inbound routing configuration on the carrier succeeds, then the number's inbound-leg status flips to configured and is independently visible from the outbound-leg status.
3. Given a number in `provisioning`, when outbound (termination) credential configuration on the carrier succeeds, then the number's outbound-leg status flips to configured independently of the inbound leg.
4. Given both inbound and outbound legs are configured, when no test call has yet been run, then the number's overall status remains `provisioning`, not `active` — configuration success alone does not promote a number to active.
5. Given a number with both legs configured, when the admin triggers "test this number" and completes the human-placed inbound call described in Constraints, then the platform confirms the inbound leg by observing that call arrive at the Gateway/Conversation Service within the stated timeout, and separately places one fully automated outbound test call to confirm the outbound leg — each leg's pass/fail is reported independently.
6. Given both test-call legs pass, when the test completes, then the number's status becomes `active` and it becomes eligible for assignment to an agent's live routing (Config Service `phone_numbers`) exactly as today.
7. Given either the inbound or outbound test-call leg fails (including the inbound leg timing out with no call observed), when the test completes, then the number's status becomes `failed` with a leg-specific, actionable error message (not a generic "provisioning failed"), and the number is not eligible for agent assignment.
8. Given a number in `failed` status, when the admin retries provisioning, then only the failed leg is re-attempted — a passing leg is not re-provisioned or re-tested.
9. Given carrier-side inbound routing configuration fails (e.g., carrier API rejects the request), when this happens, then the failure is surfaced to the admin with the carrier's error reason and the number is not silently left in `provisioning` indefinitely.
10. Given a user without `admin`/`superadmin` role for the number's tenant, when they call purchase, provision, test, or retry endpoints, then the request is rejected and no provisioning state changes.
11. Given a user scoped to tenant A, when they attempt to provision, test, or view status for a number belonging to tenant B, then the request is rejected identically to a not-found number (no information leak distinguishing "wrong tenant" from "doesn't exist" per existing cross-tenant leak precedent in this codebase).
12. Given a purchased number is later released (existing release flow), when release succeeds, then both inbound and outbound carrier-side configuration for that number are torn down, not just the platform's local record.
13. Given the DID Service has no verified live carrier credentials for a given `IDidProvider` implementation, when a developer attempts to exercise this flow end-to-end, then the PRD's acceptance criteria are understood to be verifiable only against whichever carrier has real, non-guessed credentials per this project's existing "never guess a vendor API shape" discipline — this is a build-sequencing fact, not a scope reduction.
14. Given Kamailio's DID-matching gate has been generalized per Scope to admit the purchased number's range, when a real PSTN caller dials a number in `active` status, then the call reaches Kamailio, passes the generalized gate, and is routed to the correct tenant/agent using the existing, unmodified DID→agent Redis resolution (no per-DID Kamailio dialplan edit is introduced by this feature — the gate change is carrier/range-scoped, not per-number).
15. Given a number reaches `active` status, when the Campaigns or Conversation service places an outbound call through it, then the call egresses successfully using the provisioned termination credentials without any manual carrier-console step.

## Constraints
- Concrete carrier logic must go through the existing `IDidProvider` protocol (`services/did/providers/interface.py`) — no new provider-specific branching in routers or `DidProviderManager`. Inbound/outbound provisioning are new protocol operations on the same boundary, not a parallel path.
- No `IDidProvider` implementation today exposes an operation to originate a call *into* a DID from our own side — only outbound origination (a call placed *from* the platform through the carrier) is a natural extension of the existing purchase/search protocol shape. Consequently the inbound leg of "test this number" cannot be a fully platform-triggered round trip: the admin must place one real call, from any phone, to the number under test, and the platform confirms success by observing that call arrive at the Gateway/Conversation Service (via existing call-event/CDR visibility) within a bounded timeout. The outbound leg, by contrast, is fully automated: the platform originates the test call itself through the carrier. This asymmetry is a real constraint of what the carrier boundary supports today, not a simplification of choice.
- Provisioning status (`purchased`/`provisioning`/`active`/`failed`) has no existing home in the schema: `purchased_numbers` has no status column today, and `phone_numbers.status` is a separate, already-CHECK-constrained enum owned by Config Service for a different purpose (DID→agent routing state, per `phone_numbers` schema boundaries memory). This feature's status must live in a new column/table scoped to the DID Service's own tables — it is additive, not an extension or reuse of `phone_numbers.status`.
- Trunk/routing configuration state belongs to the DID Service's own tables (alongside `purchased_numbers`), never to Config Service's `phone_numbers` table — `phone_numbers` maps DID→agent only and must not gain provider config or routing-policy columns (project memory: phone_numbers schema boundaries).
- The Gateway's DID→tenant/agent lookup stays Redis-only on the call path; this feature must not introduce any Postgres/DID-Service/Config-Service call into the live call path (project memory: Architecture Decisions, hot/cold path split).
- Kamailio's per-DID dialplan stays generic and is never edited per number (project memory: Architecture Decisions §DID routing). The one change this feature requires — generalizing the hardcoded `788`/`500[0-9]` match at `scripts/kamailio/kamailio.cfg.tpl:665` — must be scoped to "any number/range this platform has purchased and activated," configured once per carrier/range, never edited per individual DID as new numbers are purchased.
- Authorization follows the existing pattern in `services/did/routers/numbers.py`: mutating actions (purchase, release, and by extension provision/test/retry) require `require_role("superadmin", "admin")`; scope every query and mutation by the caller's `tenant_id`, and return the same not-found response for "wrong tenant" and "doesn't exist" (project memory: cross-tenant response parity).
- Every provisioning/test/retry action must call through `services/did/audit.py` the same way `purchased_numbers.py`'s existing actions do — no new unaudited mutation path.
- No concrete `IDidProvider` implementation (Plivo/Twilio) is verified against live credentials yet (per `services/did/providers/interface.py` docstring) — this feature's inbound/outbound provisioning calls must be built against the same "no guessed vendor shape" discipline, confirmed against a real trial account before merging provider-specific code.

## Open questions
1. Which carrier gets the first verified `IDidProvider` implementation this feature is built and tested against — Plivo or Twilio? This determines what the automated outbound test call in AC5 is actually exercised against, and blocks writing the concrete provisioning/test-call code until decided.
2. Who bears the cost of the automated outbound test-call leg in AC5 (platform or tenant), and is there a per-number or per-tenant rate limit on retriggering "test this number"? Not specified in the request; affects whether AC5/AC8 need a cooldown or quota check.
3. What is the acceptable timeout for the human-placed inbound test call in AC5/AC7 before the platform reports the inbound leg as failed rather than still pending? Affects the test's usability (too short: real admins fail legitimate tests; too long: "test this number" feels broken).
