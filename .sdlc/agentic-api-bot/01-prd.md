# PRD: Agentic API Task Execution (Multi-Level Tool Chains)

## Problem
Today an agent's Tool Execution Framework (`services/conversation/tools/`) can only call a small, hardcoded set of executors — `book_appointment`, `cancel_appointment`, `reschedule_appointment`, `send_sms` — each hand-written against one specific provider SDK (Cal.com, Twilio) and registered in code (`services/conversation/tools/registry.py`). Adding any new capability requires an engineer to ship a new executor class; a tenant cannot expose their own backend/CRM/ticketing API to their agent without an engineering change. The orchestrator (`services/conversation/tools/orchestrator.py`) also caps iteration at `DEFAULT_MAX_TOOL_ITERATIONS = 2` and treats every tool call as independent — it has no concept of one call's result being *required input* to a later call beyond what fits in one extra LLM round-trip, and no way to fail one specific step in a chain without discarding the whole turn's progress. A tenant who wants "look up the caller's account, then use the account ID to check their order status, then use the order ID to trigger a refund" cannot build that today at any layer — RAG retrieval answers questions about content, and the fixed executors don't compose.

## Scope
- In: A tenant admin can register a custom API (name, description, endpoint, method, request schema, auth reference) without an engineer writing an executor, scoped to their own tenant, the same way `tool_provider_configs`/`agent_tool_policies` already scope Cal.com/Twilio tools today.
- In: When registering a custom API, the tenant admin declares that API's own dependencies up front — which upstream API(s) must run first, and for each of this API's input parameters, whether it is a literal value, a value the LLM/caller must supply, or a value sourced via a JSON path into a named upstream API's response. This declared graph, not the LLM, is what the execution engine follows.
- In: No matter how many custom APIs a tenant registers, they add exactly one new entry to the LLM's tool list — `execute_api` (targeting one of the tenant's registered APIs) — alongside the existing `knowledge_search` (today's RAG path). This is additive to, and does not replace or reduce, the legacy hardcoded tool schema entries (`book_appointment`, `cancel_appointment`, `reschedule_appointment`, `send_sms`), which are unchanged and continue to appear as their own separate entries when enabled. The LLM's job is to pick the target API and supply the leaf inputs that must come from the user — never to decide the order of upstream calls itself.
- In: All `execute_api` chain resolution and outbound HTTP execution runs in a new, separate service from the conversation service, resolving and running the tenant's declared dependency graph deterministically up to 4 levels deep in a single conversational turn.
- In: When any call in a chain fails, the caller gets an honest, in-character response about what could and couldn't be completed — never a fabricated "done" for a step whose downstream dependency failed (same non-fabrication posture already enforced for bookings — see `pipeline.py`'s `_claims_booking_without_tool_call`).
- In: An operator/admin can see, per call, which APIs were invoked, in what order, with what result, sufficient to debug a failed chain after the fact.
- In: A new "Knowledge Base" section in the admin UI with two sub-tabs — "Documents" (today's RAG document management) and "APIs" (register a custom API, its auth, its parameters, and its declared upstream dependencies).
- Out: A visual chain-builder / no-code UI for wiring dependencies beyond a straightforward per-parameter "source: literal | caller-supplied | JSON path from API X" form — a graphical DAG editor is a separate design decision.
- Out: Replacing or modifying the existing hardcoded calendar/SMS executors — they continue to work unchanged; this is an additive capability alongside them.
- Out: RAG/knowledge retrieval changes to the retrieval logic itself (`services/knowledge/`) — this PRD is scoped to how retrieval is exposed and to the new API-calling path, not to ranking/embedding/chunking behavior.
- Out: Cross-tenant or cross-agent API sharing — a registered API is only ever usable by the tenant that owns it, same isolation `tool_provider_configs.tenant_id` already enforces.
- Out: Per-call request signing (HMAC) as a supported auth scheme for a registered API — only API key, static bearer token, and OAuth2 client-credentials are in scope (see Constraints).

## Acceptance criteria
1. Given a tenant admin registers one or more custom APIs (name, description, endpoint, method, request schema, auth reference, and any declared upstream dependencies) for their tenant and enables them on one of their agents, then no matter how many custom APIs are enabled, exactly one additional LLM-facing tool schema entry is ever added for all of them combined — `execute_api` — with every registered custom API reachable only as a target of `execute_api`'s own arguments, never as its own separate tool schema entry; this "exactly one entry for all custom APIs" count is independent of, and additive to, whatever legacy hardcoded tools (`book_appointment`, `cancel_appointment`, `reschedule_appointment`, `send_sms`) that same agent already has enabled, which continue to appear as their own separate schema entries unchanged.
2. Given an agent has a custom API enabled, when the caller's request requires it, then the LLM's `execute_api` call results in a real HTTP call (executed by the new API-execution service) and the caller hears a response derived from the real result — never a narrated success with no call made (same class of check as today's fabricated-booking guardrail).
3. Given a tenant admin has declared that API B's input parameter X is sourced via a JSON path into upstream API A's response, when the LLM's `execute_api` call targets B (supplying only the leaf/caller-supplied inputs), then the execution service resolves and calls A first, extracts X via the declared path, and calls B with it — the LLM never supplies X itself and never decides to call A separately.
4. Given a tenant admin has declared a 3-4 level dependency chain ending in API D, when the LLM's `execute_api` call targets D, then the execution service runs every upstream API in the declared order automatically, and the final response to the caller reflects the outcome of the whole chain (e.g., it can reference what was looked up at level 1 while confirming what happened at level 4), not just the deepest call in isolation.
5. Given a chain where an intermediate call fails (timeout, non-2xx, malformed response), when the chain cannot proceed because a later step's declared input was never produced, then the caller is told the operation could not be completed — the agent never claims a downstream step succeeded.
6. Given a chain where an intermediate call fails, when a partial result was already produced by an earlier successful call, then that partial state is not silently lost — the turn's response and the persisted record both reflect what did and didn't complete.
7. Given an API call in a chain times out, when the configured per-tool timeout (mirroring `agent_tool_policies.timeout_ms`) elapses, then the chain stops at that step with a `TIMEOUT` result and does not retry indefinitely or hang the turn.
8. Given a caller barges in (interrupts) while a multi-step chain is mid-execution, when the interruption is detected, then the in-flight chain is handled the same way a single in-flight tool call is handled today (stop waiting on it; do not resurrect it into a stale turn) — the multi-step case must not bypass existing barge-in behavior.
9. Given an agent has no custom APIs enabled, when a turn runs, then behavior is byte-identical to today's tool-calling path — no added latency, no `execute_api` target offered, same as the existing "no tools enabled" default.
10. Given a custom API belonging to Tenant A, when Tenant B's agent tries to reference or enable it (directly, or as a declared upstream dependency of one of Tenant B's own APIs), then the request is rejected — API visibility is tenant-scoped exactly like `tool_provider_configs.tenant_id` scopes existing tools.
11. Given a tenant admin declares a dependency chain deeper than the platform's maximum of 4 levels (or a lower per-agent override configured the same way `agent_tool_policies` overrides other framework defaults), when the API is saved, then registration is rejected with a clear error before it can ever be enabled on an agent — a chain this deep never reaches runtime execution at all. As a second, independent backstop, if a chain is ever presented for execution at runtime deeper than the enforced ceiling, execution stops with a clear, non-fabricated failure rather than looping or silently truncating.
12. Given a custom API is configured with one of the three supported auth schemes (API key in a header or query parameter, static bearer token, or OAuth2 client-credentials), when the tool is invoked, then the execution service authenticates the outbound call accordingly (fetching/reusing a cached OAuth2 access token and refreshing it on expiry, for that scheme); given the configured credential reference is invalid or missing for any scheme, the call fails as `UNAVAILABLE`/`FAILED` and never sends a request with no credential, and the credential reference itself is never leaked in any user-facing or logged response.
13. Given two registered APIs have no declared dependency between them, when the LLM's `execute_api` calls target both in the same turn, then each executes independently, exactly as sequential/independent tool calls do today — the execution service only chains calls where the admin explicitly declared a dependency, never inferred from timing or topic.
14. Given a completed or failed multi-step chain, when an operator inspects that call's tool-call history afterward, then every step's target API name, arguments used (including which came from a prior step's output), and result status are visible and attributable to that specific call, subject to the redaction constraint below.
15. Given a chain step has already executed a side-effecting (non-idempotent) call successfully, when a later step in the same chain fails and the turn/chain is re-invoked (by the LLM, the caller repeating themselves, or any retry path), then the already-completed side-effecting step is not automatically re-executed — either it is invoked with the same idempotency key so a duplicate is safely rejected/deduped by the downstream API, or the framework refuses to auto-retry a chain past a completed side-effecting step and requires a fresh, explicit tool call instead.
16. Given a tenant admin navigates to the agent's "Knowledge Base" tab in the admin UI, when the tab loads, then it presents two sub-tabs, "Documents" (today's existing document management, unchanged) and "APIs" (register/edit a custom API: name, endpoint, method, request schema, auth scheme and its reference, and its declared upstream dependencies).
17. Given a tenant admin registers a new API under the "APIs" sub-tab and declares a dependency on an upstream API that does not exist (or belongs to another tenant), when they attempt to save it, then the save is rejected with a clear error identifying the invalid dependency.

## Constraints
- Must build on the existing Tool Execution Framework, not replace it: `ToolRegistry` (`services/conversation/tools/registry.py`), `ToolPolicyResolver` (`services/conversation/tools/policy_resolver.py`), `ToolCallOrchestrator.run_turn()` (`services/conversation/tools/orchestrator.py`), and the `ToolResult`/`ToolStatus`/`ToolExecutionContext` contracts (`services/conversation/tools/types.py`) are the seams the `execute_api` tool call must compose with (from the conversation service's side), not duplicate.
- The chain-resolution/outbound-HTTP work itself must live in a new, separate service (following the existing per-service layout under `services/` — e.g. `services/conversation/`, `services/knowledge/`, `services/config/` are each independently deployable) rather than inside `services/conversation/`. Rationale: outbound third-party HTTP is slow and unbounded while the conversation service sits on the real-time turn path — a chain of 3-4 sequential calls would otherwise tie up conversation workers; a separate service isolates the outbound blast radius, keeps tenant API credentials out of the conversation process, and lets the two scale on independent curves. The conversation service's `execute_api` tool call is a request to this new service, not in-process execution.
- Tenant scoping must match `tool_provider_configs.tenant_id` and per-agent enablement must match `agent_tool_policies` (`agent_id`, `enabled`, `UNIQUE (agent_id, tool_name)`) in `database/schema.sql` — a new custom-API concept must not introduce a second, unscoped path to API visibility (lesson: an unscoped index/config is a cross-tenant leak, see `.claude/sdlc/lessons.md` #3). A declared upstream dependency is itself a reference to another API row and must be validated against the same tenant scope (see AC 10, AC 17).
- Every credential — API key, bearer token, or OAuth2 client ID/secret — must stay a reference only (`'env:...' | 'enc:...' | 'k8s:...'`), never a literal secret in the database, in logs, or in any tool-call-history view, same discipline `tool_provider_configs.api_key_ref` already documents. An OAuth2 client-credentials token obtained at runtime is a derived, short-lived artifact (cached and auto-refreshed by the execution service), not something stored as tenant config.
- The tool-call history view required by AC 14 must redact sensitive payload data, not just credential references: any argument or response field flowing between chain steps (e.g., an account ID, order ID, or other tenant-supplied business data) is subject to whatever the API's own registered schema marks sensitive, and at minimum must never be logged or displayed in plaintext anywhere a credential reference itself is already forbidden from appearing (see the credential constraint above) — visibility for debugging (AC 14) and redaction of sensitive values are both required, not in tension, and an API's registration schema must let an admin flag which fields are sensitive.
- Every side-effecting (non-idempotent) chain step must carry an idempotency key derived the same way `ToolExecutionRequest.idempotency_key` already defaults to `tool_call_id` (see `types.py`'s `__post_init__`) — re-invocation of a chain must never re-execute a completed side-effecting step under a new, distinct key; retry, if supported at all, must reuse the original key so the downstream API can dedupe, and any step the framework cannot prove is idempotent-safe must fail closed (no automatic re-run) rather than risk a duplicate mutation (e.g., a second refund).
- The non-fabrication posture (never speak a success the tool didn't actually return) must extend to every step of a chain, not just the final call — this is the same class of guarantee `pipeline.py`'s booking-fabrication detector already enforces for `book_appointment` and must not regress for chained calls.
- The platform's 4-level maximum chain depth (and any lower per-agent override) is enforced the same way `DEFAULT_MAX_TOOL_ITERATIONS` / per-tool `timeout_ms` and `max_calls_per_turn` (`agent_tool_policies` columns) already cap a turn — it must compose with those existing ceilings, not silently bypass them and let a turn run unbounded.
- Barge-in/cancellation handling for an in-flight call (`asyncio.wait` race against `cancel_event` in `orchestrator.py`'s `_execute_tool_call`) must continue to apply to each step of a chain — a chain must not become a way to make an uninterruptible tool call.
- Any authenticated identity can currently call the knowledge service's internal retrieval endpoints (`services/knowledge/routers/retrieve.py`); the new "APIs" admin-UI surface and its backing endpoints are an admin-facing capability and must sit behind the same role/auth checks `services/config/auth.py`'s `CurrentUser` (tenant_id-scoped, `None` == superadmin) already applies to other tenant-scoped config, not a bare `get_current_user` check (lesson: adding a new capability to "any authenticated user" silently grants it everything guarded only by that dependency, see `.claude/sdlc/lessons.md` #4).
- The new "APIs" sub-tab is additive to the existing per-agent tab structure (`admin-ui/app/agents/[tenantSlug]/[agentSlug]/page.tsx`'s `Tab` union and `.tabs` rendering, alongside the existing `knowledge-base` tab backed by `admin-ui/components/KnowledgeBasePanel.tsx`) — it must not change or remove the existing "Documents" behavior of that tab.

## Open questions
None. All three original open questions are resolved above: (1) chain model is admin-declared/orchestrator-resolved, not LLM-decided per hop; (2) registering custom APIs adds exactly one entry to the LLM tool list (`execute_api`), no matter how many APIs a tenant registers, additive to the unchanged legacy hardcoded tool schema entries (`book_appointment`, `cancel_appointment`, `reschedule_appointment`, `send_sms`); chain execution lives in a new separate service, and max depth is 4 levels with a per-agent override; (3) auth support is API key (header/query), static bearer token, and OAuth2 client-credentials (cached, auto-refreshed token), all credential material stored by reference only, with HMAC request signing explicitly out of scope.
