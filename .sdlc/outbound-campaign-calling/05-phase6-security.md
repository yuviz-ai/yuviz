# Security review: .sdlc/outbound-campaign-calling/05-phase6-design.md
VERDICT: RED

## Findings
1. [critical] The capacity router authorizes on role name alone (`require_role("superadmin")`). It never checks platform scope (`tenant_id IS NULL`). A tenant-scoped superadmin therefore gets platform-wide read and write over every tenant's outbound cap. — Design "Capacity router" Auth paragraph; `services/config/deps.py:69-80`
   Attack: Picture a superadmin account whose `tenant_id` is set to tenant A. That is a supported state: `PATCH /users/{id}` accepts `tenant_id` (`services/config/routers/users.py:34-60`), and the codebase guards this exact principal elsewhere. `routers/audit_log.py:22` says "a tenant-scoped superadmin only sees its own tenant's rows", and `routers/users.py:23` requires `is_platform_scoped(...) and role == "superadmin"`. This account calls `GET /capacity/tenants` and receives every tenant's name, slug, cap and live in-flight count. It then calls `PUT /capacity/tenants/{B}` with `1`, which throttles tenant B's campaigns to one call. It can also raise its own cap or rewrite the platform limits and CPS for everyone. This is cross-tenant read and write by a principal that every sibling route confines to tenant A. Lesson 24 covers this case.
   Fix: Make the router dependency require `role == "superadmin" and is_platform_scoped(user)`, and keep the same 403 body. Add a tenant-scoped-superadmin principal to the AC2/AC3 403 matrix in `test_capacity_routes.py`. Gate `CapacityCard` on platform scope too, not just `role === "superadmin"` (`admin-ui/lib/useConnectionAccess.ts:27`).

## Verified controls
- `require_role` is an `async` dependency that depends on `get_current_user`, so it re-reads the user row through `fresh_console_authority` (lesson 27). As a router-level `dependencies=[...]` entry, FastAPI awaits it (lesson 38).
- The 403 text depends only on the caller's role (`deps.py:77`), and path params are typed `str`. For one principal the response is the same for its own tenant id, another tenant's id and a random UUID (AC3, lesson 2). One caveat: FastAPI parses a malformed JSON body before dependencies run, so a non-superadmin sending broken JSON to a PUT gets 400, not 403. That carries no tenant or existence signal, but the "role check before any body handling" claim and the AC2 test should account for it.
- Service accounts (`viewer`, NULL tenant) fail the role check, so they get 403 on all capacity routes.
- `GET /tenants/{tenant_id}/campaigns/caller-ids` sits on `tenant_scoped_router`, which inherits `bind_path_tenant` and `require_path_tenant_access` → `assert_tenant_access` (`deps.py:91-125`). A tenant-B admin gets 403 for tenant A's id (UUID branch) and 404 for an unowned slug. The query also carries an explicit `pn.tenant_id = $1` predicate and `tc.tenant_id = pn.tenant_id` on the join, so it does not depend on RLS, which is inert here (lessons 36 and 48).
- Adding the route creates no `{campaign_id}` route, so there is no collision with the `/campaigns/{campaign_id}` router.
- The attempts disposition join keys on `a.tenant_id = $2`, `t.id = a.tenant_id` and `k.tenant_id = t.slug AND k.session_id = a.call_session_id`. It reads only `disposition`, and only when `answered_at` is set, so there is no cross-tenant `calls` read.
- `_mask_callee` pops the raw `callee` inside `list_for_campaign`. Every `failure_reason` the worker writes is a fixed enum (`deadline`, `end_not_observed`, `dial_rejected`, `no_sip_node`, `superseded`), so no other attempts column carries the number. No capacity response contains a callee. The new readiness warning log has no exception text. `platform_conn` logs only `reason`.
- Callee masking is uniform across attempts and capacity. The contacts list still returns the full `phone_number` to the same tenant (OQ2). That is an accepted product decision, not a leak across tenants.
- Audit visibility: capacity audit rows carry no callee. The only `audit_log` reader is the superadmin-only `/audit-log` route, and for non-platform callers it adds an explicit `tenant_id = $n` predicate (`services/config/audit.py:56-90`). No tenant admin or viewer can read limit-change rows. A tenant-cap row is stamped NULL at write time (no `stamp_tenant`). `rls.sql`'s `entity_type='tenant'` backfill may later stamp it with that tenant's id, which only that tenant's own (scoped) superadmin could see. Platform and CPS rows stay NULL, so only the platform superadmin sees them. The design should state which stamping it intends.
- Strict pydantic schemas plus the new `RequestValidationError` handler drop `input`/`ctx`, so request values are not echoed back. `LimitError` reaches the client only through the existing `ValueError` → 400 handler.
- Each capacity write runs as lock → read old → set → `write_audit` in one transaction, so a rejected write leaves no audit row (AC9). Admission uses plain reads and is not blocked by the lock.
- UI role surfaces: write controls are hidden until `checked` (fail closed). `listCampaignCallerIds` is called only from `SettingsSection`, which mounts only for `canManage`. A viewer's write attempts are still refused server-side by `require_role("superadmin","admin")` on start, pause, resume and PATCH. Section fetches are independent (no `Promise.all`, lesson 21).
- No new listener or bind: the routes ride the existing Campaigns `:8400` JWT-authenticated app.
