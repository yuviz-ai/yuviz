# Code review (round 2, backend)
VERDICT: RED

Round 1 finding 1 is not fixed. The upload/worker mismatch is gone, but national numbers are now turned into well-formed E.164 for the wrong country, and legacy rows are untouched. Round 1 findings 2–6 are outside this diff and carried forward unchanged.

1. [blocking] A national number gets `+` prepended, which makes it a valid number in a different country — `services/campaigns/campaign_contacts.py:25-28` — fails when: a CSV row is `9876543210` (an Indian mobile number, the exact example from round 1) or `09876543210`. Both are stored as `+9876543210`, which `is_e164` accepts, so the worker dials country code +98 (Iran). `415.555.2222` becomes `+4155552222` (+41, Switzerland), and the updated test at `tests/test_campaign_contacts.py:50` asserts that as correct. Before, the contact failed safely. Now it places an international call to a stranger, at international rates, with the calling-hours and DNC/consent checks applied to the wrong person. Stripping the leading `0` is a national trunk-prefix rule, and it only makes sense once you know the country. — fix: do what design A10 says. Normalise with `did_format.to_e164(raw, campaign.default_country)` (phonenumbers `is_valid_number`), and reject a number without `+` with `no_default_country` when no country is set.

2. [blocking] Legacy contacts without `+` are still burned by the worker — `services/campaigns/worker.py:245` / `database/schema.sql` (no campaign_contacts phone backfill) — fails when: a campaign has `pending` contacts uploaded before this change (stored as `9876543210`, `4155552222`, ...). Upload normalisation never touches them, and the worker's `is_e164` check marks every one `failed` with no retry. The round 1 finding named this case ("old contacts without `+`"), and nothing in this round handles it. — fix: when the worker sees a non-E.164 number, normalise it with the campaign's default country (or a backfill that does the same), and park it as blocked or needing a country instead of failing it for good.

3. [minor] A user-typed `+0` prefix is silently rewritten, and the standard `00` international prefix is rejected — `services/campaigns/campaign_contacts.py:27` — fails when: a row is `+0919876543210`, a typo that should be rejected. It is quietly turned into `+919876543210`. A correctly written international number like `00919876543210` gives `+0919876543210` after one `0` is stripped, which fails `is_e164`, so the whole upload is rejected. — fix: this goes away with finding 1's `to_e164`. Otherwise, never change input the user already gave with `+`.

4. [minor] The tests do not cover the cases this fix claims to handle — `services/campaigns/tests/test_campaign_contacts.py:47-69` — fails when: there is no test for a leading `0`, a too-short or 16+-digit number, `+0`, or a number without `+` that must be rejected or mapped to a known country. The one changed assertion pins the wrong-country output (`+4155552222`), so a correct fix would fail it. Lesson 12: this test could not catch the defect it was meant to guard against. — fix: add table-driven cases for each input class, with expected values that are correct per country.
