# Code review
VERDICT: RED

1. [blocking] Upload accepts numbers the worker then fails permanently — `services/campaigns/campaign_contacts.py:50` / `services/campaigns/worker.py:245` — fails when: a CSV row is `9876543210` (or `09876543210`, or any legacy pre-migration contact stored without `+`): `_DIAL_NUMBER_RE` (`\+?[0-9]{3,15}`) accepts it, then `_dial_next`'s `is_e164` check marks the contact `failed` with no retry, so the whole list is silently burned and never dialled. The design (A10, CSV bullet) requires upload to normalise to E.164 via `did_format.to_e164` and reject anything that fails. — fix: normalise to E.164 at upload (and for legacy rows) as the design says, or reject non-E.164 at upload so both checks agree.

2. [minor] Webhook nonce is used up before the event is published — `services/telephony/app.py:123` (vs `:138`) — fails when: `claim_webhook_nonce` SET NX succeeds, then `_publish`'s XADD raises (for example, the new Redis ACL is missing XADD on `STREAM_CPAAS`, or a transient Redis error). The handler returns 500 and the provider retries with the same nonce, which now gets 403 "replay", so the hangup event is lost for good and the attempt can only close at its deadline. — fix: publish first and claim the nonce after, or delete the nonce key when publish fails.

3. [minor] Reconcile scans a fixed 200-row window with no cursor — `services/campaigns/attempts.py:95` — fails when: 200 or more attempts across the platform stay unresolved (pending/sent, ordered first). Answered attempts (`state='resolved'`, sorted last) are then never read, so a call whose hangup event was lost is never closed by `end_overdue`. It stays counted in `IN_FLIGHT`, and campaign, tenant and platform capacity leaks until the backlog drains. — fix: fetch the answered/end-overdue rows in a separate query, or page with a cursor.

4. [minor] `_sending` guard can never trigger (dead code) — `services/campaigns/worker.py:113` — fails when: never. `_reconcile` and `_send_sip`/`_send_cpaas` run one after another in the single `_tick` task and every send is awaited inline, so the set is always empty when `_reconcile` reads it. It also does nothing against a second worker process. A later reader will wrongly assume this set provides cross-send safety. — fix: remove it, or move the guard to the DB (`state`/`last_send_at`) if concurrent senders are expected.

5. [minor] Superseded helpers left behind with no non-test callers — `services/campaigns/campaign_contacts.py:98` (`claim_next_pending`, which this diff still edits), `:160` (`release_claim`), `services/campaigns/telephony_originate.py:131` (`poll_idempotency`) — fails when: someone reuses `claim_next_pending`. It claims a contact without creating a `campaign_attempts` row or taking the admission lock, so the contact sits in `calling` with no attempt, outside capacity accounting, and is never resolved by reconcile. — fix: delete all three.

6. [minor] Reconcile request sends fields the server drops — `services/campaigns/telephony_originate.py:165` vs `services/telephony/app.py:186` — fails when: a provider's `reconcile_call` needs `to`/`from`/`created_after` to find a call that was placed without the reference tag. `ReconcileBody` silently ignores those fields, so the call reports `unknown`, the attempt fails at its deadline and the contact is re-dialled with a new key (a double call). — fix: either add the fields to `ReconcileBody` and pass them through to `outbound.reconcile`, or stop sending them.
