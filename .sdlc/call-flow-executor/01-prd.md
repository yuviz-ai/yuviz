# PRD: Call-flow executor (IVR runtime for published call flows)

## Problem
A tenant can author, validate, and publish an IVR call flow today (`services/config/call_flows.py`, the Admin UI's call-flow editor), and a phone number can be bound to it transitively through `phone_numbers.agent_id -> agents.call_flow_id`. But nothing ever executes it: `libs/config_sdk/interfaces.py`'s `IConfigProvider` has no `get_call_flow`, and no runtime walks the graph on a live call. Every inbound call today either goes straight to the conversational agent or gets whatever the gateway's default routing does — a caller dialing a number with a published IVR hears nothing of it, and every DTMF-driven menu, digit collection, or transfer step a tenant built is dead configuration.

## How this is solved elsewhere
This is a solved shape (Twilio Studio, Amazon Connect, Genesys, Five9) and the request has already fixed the hard architectural fork (in-process, Python, cache-no-lock, version pinned at session open) — so research here is scoped to runtime *mechanics*, not the build-vs-buy or service-topology question.

- **Digit collection and timeout convergence**: Twilio's `<Gather>`/Gather-Input widget defines number-of-digits, a stop-gathering keypress (terminator), and a timeout, and submits whatever was collected when the timeout fires rather than erroring — same shape as this codebase's `collect` node (`min_digits`/`max_digits`/`terminator`/`timeout_ms`). Twilio also cuts off collection early the instant the digit count hits its configured max, without waiting for the terminator or the timeout — worth adopting here (AC 16) since the node model already carries `max_digits` for exactly this purpose. (unverified: Twilio's own retry/`maxAttempts` semantics beyond timeout submission — their docs push retry logic into the flow graph itself, i.e. wiring the timeout output back to the same Gather, which is functionally identical to this model's `max_retries` counter and requires no additional primitive.)
- **Version pinning at session open**: Amazon Connect versions contact flows immutably and lets an operator target a specific version by ARN, but its public docs do not state whether an in-progress contact rides out a flow that gets updated mid-call (unverified). This PRD does not need that answer — the user's decision to pin the graph at session open is stricter than "unverified" and is the right default for a live phone call regardless of what Connect does: a caller must never have the ground shift under them mid-conversation.
- **Recommendation / what to cut from the request's shape**: nothing to cut — the request's decisions (in-process, cache-the-graph-no-lock, pin-at-open) already match where the market converges (flow graphs are treated as immutable per-version documents, fetched once, walked locally). The one mechanic worth importing is Twilio's "auto-submit at max digit count" rule for `collect`, folded into the acceptance criteria below.

## Scope
- In: Resolve an inbound call's DID to its tenant, agent, and (if the agent has one) published call flow, reusing the existing Redis-first `did:{did}` resolution — no new DID-resolution mechanism.
- In: Load and cache the call flow's published graph so that concurrent calls to the same number share one Postgres read per published version, with the graph pinned per-session at call open regardless of any publish that happens afterward.
- In: Execute all seven node types (`start`, `play`, `menu`, `collect`, `dial`, `agent`, `hangup`) with prompt playback, DTMF menu branching (including timeout, invalid keypress, and retry exhaustion), and digit collection into named variables.
- In: Hand off at an `agent` node to the conversational agent it names, carrying every variable collected earlier in the flow into that agent's session.
- In: Degrade every resolution/parse failure in this path to a safe default rather than rejecting or crashing a live call, matching the contract already documented in `services/conversation/agent_resolver.py`.
- Out: Outbound/OBD call flows (`call_flows.direction = 'outbound'`) — this PRD covers only a caller-initiated inbound call.
- Out: Call-flow authoring, validation, draft/publish, and version-history UI/API — already built (`services/config/call_flows.py`, `services/config/routers/call_flows.py`, the editor).
- Out: Any UI/API to see which node a live call is currently sitting on — that is a live-call-monitoring concern, not this executor; see Open Questions.
- Out: Changing the DID-to-tenant/agent Redis cache's shape, key, or no-TTL policy (`services/config/phone_numbers.py`) — that mechanism is a constraint this feature reads, not something it modifies.
- Out: Post-transfer call outcome (busy/no-answer/failure) on a `dial` node — the executor's responsibility ends at handoff to the dialed destination; what happens to the call afterward is not this feature's concern.

## Acceptance criteria

Resolution and caching
1. Given an inbound call lands on a DID whose resolved agent (via the existing `did:{did}` cache) has a `call_flow_id` pointing at a published call flow, when the call is answered, then the session starts by executing that flow's `start` node, not the conversational agent directly.
2. Given the resolved agent has no `call_flow_id`, when the call is answered, then the call-flow executor is not invoked at all and the call proceeds straight to the conversational agent exactly as it does today, unaffected by this feature.
3. Given N concurrent inbound calls open sessions against the same published call flow within the graph cache's lifetime, when each session resolves its flow, then Postgres is read at most once for that flow's published graph; every other session is served from cache.
4. Given a call flow is republished (its `config_version` increments) while a call is already mid-flow on the previously published version, when that call advances to any subsequent node, then it continues walking the graph it was pinned to at session open — never the newly published one.
5. Given a call flow is republished, when a new call arrives after the publish has completed, then that new call is pinned to the newly published version's graph.
6. Given two calls open sessions concurrently against the same call flow (same or different callers), when both execute simultaneously, then each holds its own independent active-node pointer and variable set, with no shared mutable state or lock required between them for either to behave correctly.
7. Given a phone number's `status` is not `'active'`, or the DID row is soft-deleted, when a call attempts to reach it, then no call-flow resolution happens at all — this is unchanged from today's existing DID-miss behavior and is not modified by this feature.

Node behavior — happy path
8. Given a `start` node, when its session opens, then the session's TTS voice is set from `start.tts_config_id` (falling back to the tenant/account default voice when unset), the node speaks nothing itself, and execution immediately advances along its single outgoing edge.
9. Given a `play` node, when it is reached, then its rendered prompt is spoken in full, then execution advances along its single outgoing edge.
10. Given a `menu` node and a caller presses a digit with a matching branch edge, when that keypress is received, then execution advances along that matching edge without waiting out the remainder of `timeout_ms`.
11. Given a `collect` node, when the caller presses digits followed by the configured `terminator` and the accumulated digit count is `>= min_digits`, then the accumulated digits (terminator excluded) are stored into `variable` and execution advances along the node's single outgoing edge.
12. Given a `collect` node, when the accumulated digit count reaches `max_digits` before the terminator is pressed, then the node submits immediately with the digits collected so far, without waiting for the terminator or for `timeout_ms` to elapse. *(Assumption: matches the "stop after N digits" convention converged on elsewhere; not stated explicitly in `libs/config_sdk/callflow.py` today — flagged in Open Questions.)*
13. Given a `dial` node, when it is reached, then its pre-transfer prompt (if set) is spoken and the call is handed to `destination`; the executor's involvement with that call ends at this node, consistent with `dial` being terminal in the graph model.
14. Given a `hangup` node, when it is reached, then its prompt (if set) is spoken and the call is then ended.

Node behavior — menu timeout, invalid keypress, retry exhaustion
15. Given a `menu` node times out waiting for a keypress and the node has an explicit `timeout` branch edge, when the timeout fires, then execution takes that edge immediately — this does not consume a retry.
16. Given a `menu` node times out waiting for a keypress and the node has no explicit `timeout` branch edge, when the timeout fires, then the node's prompt is replayed and a retry counter for that node-visit is incremented.
17. Given a caller presses a digit with no matching branch edge on a `menu` node that has an explicit `invalid` branch edge, when that keypress is received, then execution takes the `invalid` edge immediately — this does not consume a retry.
18. Given a caller presses a digit with no matching branch edge on a `menu` node with no explicit `invalid` branch edge, when that keypress is received, then the node's prompt is replayed and a retry counter for that node-visit is incremented.
19. Given a `menu` node's retry counter reaches `max_retries` through any combination of un-branched timeouts and un-branched invalid keypresses, when the next such event would trigger another replay, then the call is ended by a clean hangup instead of looping or being replayed again.
20. Given a `menu` node defines both a `timeout` and an `invalid` branch, when either fires, then it never counts toward `max_retries` at all, since an explicit branch is always taken immediately regardless of how many times the node has already been visited.

Node behavior — collect short/late/failed input
21. Given a `collect` node, when the terminator is pressed but the accumulated digit count is `< min_digits`, then the attempt is treated as invalid input: the prompt is replayed and the node's retry counter is incremented (same accounting as a `menu`'s un-branched invalid case). *(Assumption, flagged in Open Questions — the node model has no dedicated "collect failed" branch, so this mirrors the menu's un-branched handling.)*
22. Given a `collect` node, when `timeout_ms` elapses with the terminator never pressed and the digit count still `< max_digits`, then the attempt is treated as invalid input using the same replay-and-increment handling as AC 21.
23. Given a `collect` node's retry counter reaches `max_retries` under AC 21 or AC 22, when the next attempt would trigger another replay, then the call is ended by a clean hangup instead of proceeding with a value shorter than `min_digits`. *(Assumption, flagged in Open Questions.)*

Node behavior — agent handoff
24. Given an `agent` node is reached, when the handoff occurs, then the live call is handed to the conversational agent named by `agent_id`, and every variable collected by any `collect` node earlier in this call's flow is seeded into that agent's session as initial variables (same seeding mechanism `WorkflowRunner` already uses for call-context variables).
25. Given an `agent` node's `agent_id` resolves to an agent belonging to a **different tenant** than the call flow's own tenant, when the handoff would occur, then it is refused — the call must never be connected to another tenant's agent; it degrades per the Config-plane degradation criteria below instead.
26. Given the conversational agent named by an `agent` node cannot itself be resolved (deleted, deactivated, or resolution failure), when the handoff is attempted, then the call degrades per the Config-plane degradation criteria below rather than the handoff silently doing nothing or crashing the session.

Config-plane degradation (must match `services/conversation/agent_resolver.py`'s never-raise contract)
27. Given the resolved agent's `call_flow_id` points at a call flow that no longer exists (hard-referenced row missing) or is soft-deleted, when the call is answered, then the executor is skipped and the call proceeds to conversational-agent resolution exactly as it would for an agent with no `call_flow_id` (AC 2) — never a rejected or dropped call.
28. Given the resolved call flow's published graph fails to parse at runtime (malformed JSON, a validator rule violated after being previously valid), when the call is answered, then the failure is logged and the executor degrades the same way as AC 27 — never a crash, never an unhandled exception surfacing to the caller.
29. Given any unhandled exception is raised while executing any node in an active call's flow, when that exception occurs, then the call is ended by a clean hangup rather than a dropped session, a silent stall, or a crash that takes down other concurrent calls in the same process.
30. Given a `collect`-seeded variable name collides with a call-context variable name already present on the session (e.g. seeded from telephony metadata), when the `collect` node stores its value, then the new value overwrites the old one (last-write-wins, consistent with `WorkflowRunner.update_variables()`'s existing behavior) — this collision is never treated as an error.

Tenant isolation (explicit, since this path resolves a caller's DID into a tenant and then reads RLS-protected tables)
31. Given a call flow row belongs to tenant A, when a call is routed to tenant B's DID, then no code path in this executor can load tenant A's graph for that call — verified by the executor requiring the DID-resolved tenant to be set as the active RLS target before any `call_flows`/`call_flow_versions` read, not merely trusting a `call_flow_id` value in hand.
32. Given the executor's process identity is platform/service-scoped (no caller tenant of its own, `tenant_id IS NULL`, per the existing convention in `libs/tenancy/session.py`), when it is about to read `call_flows` or `call_flow_versions` for a given call, then it must have explicitly set the DID-resolved tenant as the RLS target for that read; an executor that reads with no target tenant set must raise `TenantUnresolved` rather than silently returning no rows or, worse, another tenant's row.
33. Given a phone number is deactivated or its agent binding changes while a call is already in progress and pinned to a flow (AC 4), when that call continues, then it is unaffected by the change; only calls that open **after** the change see the new resolution.

## Constraints
- Node model, terminal-node rules, DTMF key set, and menu/collect fields are exactly those defined in `libs/config_sdk/callflow.py` (`NODE_TYPES`, `TERMINAL_NODE_TYPES`, `DTMF_KEYS`, `MENU_TIMEOUT`/`MENU_INVALID`, `CallFlowNode` fields) — this PRD introduces no new node type, field, or DTMF vocabulary.
- DTMF reaches the *vobiz* process today but does **not** reach `services/conversation`, and closing that gap is in scope. `services/vobiz/bridge.py`'s `_vobiz_to_grpc()` already receives a `kind == "dtmf"` websocket event from the gateway, shaped `{"event": "dtmf", "dtmf": {"digit": <key>}}`, at lines 342-343 — but unlike the `media` branch directly above it (which builds `pb.GatewayMessage(audio_chunk=...)` and forwards it over gRPC), the `dtmf` branch only logs the digit and forwards nothing. `GatewayMessage`'s `oneof payload` in `proto/voiceai/v1/conversation.proto` has eight arms and none of them carry DTMF. Therefore a keypress currently never crosses the vobiz→conversation gRPC boundary where this executor lives: **a new `GatewayMessage` oneof arm for DTMF (and the `bridge.py` forwarding to populate it) is required work, not a no-op.** The gateway-side event shape above is the input contract — the `digit` field is the keypress value for AC 10, 15-18 and 21-22 — but the proto message and the forwarding branch must be added. The exact proto message shape and field numbering is a design decision, not a product one.
- Per the request's binding decisions: implementation is Python, in-process in `services/conversation`, as a sibling to `WorkflowRunner` (`services/conversation/workflow/runner.py`) — not a separate service, not Java, and with no per-flow or per-caller lock. The graph cache mirrors `WorkflowRunner`'s module-level `_GRAPH_CACHE` keyed by `(tenant, agent)` and versioned by `config_version`; the equivalent here is versioned by the call flow's own `config_version` (`call_flows.config_version`, incremented by `publish()` in `services/config/call_flows.py`).
- DID resolution reuses the existing Redis-first `did:{did}` cache verbatim (`services/config/phone_numbers.py get_by_did`) — no-TTL by deliberate design (see that file's top-of-module comment); this feature must not introduce any new TTL on that key or duplicate its resolution logic.
- Any config-plane failure must degrade to a default and never reject or crash a live call — the exact behavior already specified and implemented in `services/conversation/agent_resolver.py resolve_handler_deps()` (catches everything, returns `None`, caller falls back).
- Tenant scoping follows `libs/tenancy/session.py`'s existing model: `set_target_tenant()` before any tenant-scoped read, `current_tenant()`/`TenantUnresolved` as the enforcement point, and the `caller`-is-`None` platform-scoped-service-account pattern already used by other cross-tenant service reads (lesson 24) — this executor is exactly such a service account, resolving many tenants' DIDs from one process.
- Variable seeding across the `agent` handoff must use the same mechanism `WorkflowRunner.__init__`'s `variables` parameter and `update_variables()` already provide — not a new state-passing channel.

## Open questions
1. **Observability of node position**: how (if at all) does a live-call-monitoring surface show which node an in-progress IVR call is currently sitting on? Not designed in this PRD; flagged since the git history shows a `live-calls-monitoring` feature already in flight that may need this.
2. **Collect node failure/auto-submit semantics** (ACs 12, 21, 23): the node model does not itself define max-digit auto-submit, short-digit-at-terminator handling, or retry-exhaustion behavior for `collect`. This PRD assumed behavior mirroring the `menu` node's already-commented "replay then give up" contract (`libs/config_sdk/callflow.py`'s `graph_warnings()`) — confirm before implementation, since a different choice (e.g., proceeding with a short value instead of hanging up) changes what "done" means for this node type.
3. **Blank/empty `terminator`**: `CallFlowNode.terminator` defaults to `"#"` but is a plain `str`, so an author could set it to an empty string. No submission rule is defined for that case (submit purely on `max_digits` or `timeout_ms`?) — not addressed by this PRD.
4. **Default target on call-flow-specific resolution failure** (ACs 27–28): this PRD assumes "skip the IVR, fall through to conversational-agent resolution" is the correct default, by analogy with `agent_resolver.py`'s existing None-returns-fallback contract. That contract was written for agent/tenant resolution, not specifically for a call-flow layer sitting in front of it — confirm this is the intended default rather than, say, playing a fixed apology prompt and hanging up.
