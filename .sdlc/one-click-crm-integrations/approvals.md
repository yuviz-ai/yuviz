## security — 2026-10-02

FIX Security round-3 finding 1 [high], OQ9 fence governs `spoken` but `items` reaches the model unconditionally — I verified the trace myself rather than taking the reviewer's word: `services/conversation/tools/orchestrator.py:179` calls `_fold_tool_result_into_history(history, event, result)` and only *then* does line 180 test `result.deterministic_response is not None` and return. The fold is unconditional and pre-emptive, so the deterministic short-circuit suppresses narration of one turn while `full_name`/`company`/`owner_name` stay in `history` for the rest of the call. This is shipped runtime code the design does not change, which is exactly why the fence as written is not a control — lesson 1: naming a mechanism is not specifying it, and lesson 13's shape, a guard placed after the thing it is meant to gate. Not escalated as a mechanism question because the reviewer's fix is strictly narrowing, closes the channel by construction rather than by prose, and dissolves finding 3 for v1; the *product* question underneath it is escalated separately below. — Owner: architect, `.sdlc/one-click-crm-integrations/02-design.md`, projection step 4 + the OQ9 paragraph + the Risks "greeting template" bullet: while OQ9 is open, `apply_response_transform` returns `items` entries containing **`contact_id` only**; `full_name`, `company` and `owner_name` are computed server-side for match quality and never returned. Delete the sentence "The projected fields still reach the model through `items`; what this fence governs is the deterministic line the agent speaks" — it is the design asserting the hole. Re-point test 3's disclosure assertion at the returned payload (`data` / `prior_responses` / the folded tool message), not only at the rendered success template, since the rendered template was never the leaking surface.

FIX Security round-3 finding 2 [low], extraction table omits the match phone — The table is closed for the five fields it projects but step 2's `digits_only(record_phone)` names no per-provider path and is not covered by the scalar rule, so a null or numeric `Phone` (legal in Zoho) raises inside the transform, and an implementer filling the gap by scanning for a phone-ish key reintroduces exactly the generic object walk step 3 exists to forbid. Cheap and unambiguous, so it is a fix, not a carried risk. — Owner: architect, `02-design.md` `crm_contact_projection` steps 2-3: add the three literal match paths (`Phone`, `properties.phone`, `Phone`) to the same extraction table and extend the scalar rule to them — a non-`str` phone means that record does not match.

FIX Security round-3 finding 4 [low], survivor count vs the non-`str` `contact_id` drop — Step 4's "exactly one record survived" is unordered relative to step 3's drop, so two suffix-matching records where one has a non-`str` id yield `ambiguous` under one reading and a full `match` item under the other. Criterion 22's answer must not depend on a provider data quirk. — Owner: architect, `02-design.md` projection steps 3-4: one sentence stating the drop happens in step 3 and the survivor count in step 4 is taken **after** it.

DECIDE Security finding 3 [medium], third-party-writable CRM text as an indirect prompt-injection channel — Not separately actioned. Salesforce Web-to-Lead and public HubSpot forms do make `company`/`firstname`/`lastname` attacker-authored, and ~600 chars of it in the tool message is a real instruction budget; but with finding 1's fix applied only `contact_id` leaves the transform, so for v1 the channel does not exist. Recording it rather than closing it silently, because it returns the moment OQ9 is answered Option A. — Owner: architect, `02-design.md` Risks: add one bullet stating projected CRM values are untrusted third-party text, that the v1 interim default removes the channel by returning `contact_id` only, and that any OQ9 answer which returns name fields must also cap each field at ~100 chars and delimit/escape them where the prompt and success template assemble them. This bullet is an input to the post-OQ9 security pass, not a v1 task.

ESCALATE OQ9 — what may the agent disclose to a caller whose number it cannot authenticate? — Escalated on the product criterion, not on uncertainty, and not because the security finding is unfixable. It is a genuine product choice with no defensible default: Option A (speak the matched contact's name, employer and owning rep to anyone who can spoof CLI to that number) and Option B (acknowledge a match and disclose nothing) are both positions a reasonable owner takes, and they resolve differently for a dental clinic and a B2B sales team. It is also user-visible scope: PRD criterion 21 commits that "the agent receives that contact's name and the fields needed to serve the call", and the interim default I am imposing above deliberately does not deliver that — defensible only because the lookup cannot be enabled for any tenant while OQ9 is open, so no shipped state has criterion 21 weakened. If OQ9 is answered Option A, criterion 21 is met as written and finding 3's injection cap plus delimiting become required work; if Option B, criterion 21 needs rewording to match what the agent actually receives. Either way the answer changes the artifact, so it cannot be left to the implementer. Not urgent — the feature is blocked behind connector-presets regardless — but it must be answered before `03-plan.md` is written, and it is cheapest to answer now while the design text is still the only thing that has to change. — Exact question for the user: *"When an inbound caller's number matches exactly one CRM contact, and we cannot verify the caller is that person (CLI is spoofable), may the agent use and speak the contact's name, company and account-owner name? (A) Yes — treat a phone match as good enough, accepting that a caller spoofing a number learns the contact is in your CRM plus their name, employer and owning rep. (B) No — the agent acknowledges a record exists and discloses nothing until the caller identifies themselves some other way. (C) Per-tenant setting, defaulting to B."* Record the answer in `02-design.md`'s OQ9 section and in the PRD's open-questions table, and re-state criterion 21 to match. Until it is answered, the lookup must not be enabled for any tenant — that gate belongs in the `02-design.md` STATUS banner alongside the connector-presets gate.
