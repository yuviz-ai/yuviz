# Code review
VERDICT: AMBER

1. [minor] `_crm_spoken`'s 120-char cap has no test that can fail — `services/toolexec/tests/test_executor_crm.py:357` — fails when: delete the whole `for key, lead in (...)` / `break` loop from `_crm_spoken` (`services/toolexec/presets.py:528-540`) and emit the full `"Caller matched: <100ch> at <100ch>, account owner <100ch>."`; the assertion `len(line) <= len("Contact lookup: match.") + 120` still holds because `_interpolate_success_template` already truncates each placeholder at `text[:120]` (`services/toolexec/executor.py:660`), and the single-field fixture never exercises the loop. This is the flagged "a second mechanism also blocks it" shape — fix: add a record with `full_name`, `company` and `owner_name` each ~60 chars and assert *which* fields survive the carrier sentence, not just its length.

2. [minor] Zoho's new `api_base_claim` is connect-time only, with no backfill and no reconnect signal — `services/toolexec/oauth.py:117` / `services/toolexec/presets.py:875-879` — fails when: a tenant connected Zoho before this branch (`api_base_url` NULL) applies `zoho_crm`; `apply_preset` raises `PresetConnectorRequired("connector_required")` while `ConnectorsPanel` shows Zoho with a green **Connected** badge, so the console tells the admin to connect something that is already connected. Same for any Salesforce row whose token response omitted `instance_url` — fix: flip such rows to `reconnect_needed` (or surface a distinct `connector_reconnect_required` code the panel renders as "Reconnect Zoho").

3. [minor] The client re-derives `auth_kind` that the server owns — `admin-ui/components/ConnectorsPanel.tsx:39` — fails when: a second `auth_kind="api_key"` provider is added to `PROVIDERS`; it is not in the hard-coded `API_KEY_PROVIDERS` set, so **Connect** calls `authorizeOAuthConnection`, which `start_authorization` (`services/toolexec/oauth.py:230`) now rejects with `oauth_provider_unavailable` — a dead button with a misleading error, and the API-key modal is unreachable. The provider listing returns only `{key,label}` — fix: return `auth_kind` from the providers endpoint and branch on it.

4. [minor] `api_host_suffixes` on `microsoft` is unreachable config that reads like a live allowlist — `services/toolexec/oauth.py:102` — fails when: a reader (or a later change) assumes a Dynamics token may be sent to `*.dynamics.com`. `_validated_api_base` is the only consumer and it runs only under `if spec.api_base_claim is not None` (`services/toolexec/oauth.py:325`), which microsoft leaves `None`; `provider_host_allowed` documents that it never consults suffixes. So the set is never read on any path — fix: drop it, or add `api_base_claim` when Dynamics is actually wired.

5. [minor] Two incompatible meanings of "digits only" one file apart — `services/toolexec/presets.py:476` vs `services/toolexec/executor.py:379` — fails when: `remote_party` arrives as anything but bare E.164 (e.g. `+1 415-555-0123`); the executor's `value_digits_only` branch only does `remote_party.lstrip("+")`, so Salesforce's SOSL `q` and HubSpot's `phone_digits` filter are sent `1 415-555-0123` and match nothing, while the record side is normalized by `presets.digits_only()`'s `re.sub(r"[^0-9]", "", ...)`. The outcome is a silent `no_match`, not an error — fix: have the executor's caller_id path call `presets.digits_only` (or rename `value_digits_only` to `value_strip_plus` so the asymmetry is visible).

6. [minor] httpx URL logging is quieted by exactly one call reachable from one launcher — `services/toolexec/__main__.py:9-14` — fails when: toolexec is started as `uvicorn services.toolexec.app:app` (or under any ASGI host / reload worker) instead of `python3 -m services.toolexec` (`scripts/start_local.sh:124`); `configure_logging()` never runs and every Salesforce/Zoho lookup logs the caller's number at INFO inside the request URL (`q=`, `phone=`). This feature is the first to put caller PII in a URL rather than a body, so the blast radius of that one line changed — fix: set the `httpx`/`httpcore` levels at `services/toolexec/app` import time as well, and add a test asserting both logger levels (there is none today).
